Void Crew Chat Bugs — Research Notes

Research Void Crew 1.3.0 Unity 2022.3.62 VoidManager 1.2.11 2026-07-19 · extended 2026-08-30

Written after the 26-07-19 two-client test, where chat problems blocked client-side command testing entirely: the non-host could not run !difficulty, which in turn made it look like escalation state wasn't syncing. It was — the logs show → sent / ← applied pairs matching on non-default values (see TODO, 8-E).

2026-08-30: Symptom 1 re-investigated against the Unity Vivox SDK and the decompiled adapter after the first fix attempt (the input patch) didn't stop messages going missing. The race is confirmed, the end-state corrected, the “inverted channel capability” suspicion refuted against VoidCrew.GameLibs 1.3.0, and a mod-side workaround shipped. This section absorbs what had been a separate vivox-channel-race-research.md.

Summary

Two chat symptoms were reported during multiplayer testing. Both are vanilla game bugs. Neither is caused by VoidCrewTerminus, and neither is fixed by VoidManager. Both now have a mod-side workaround, and both are shipped.

Bottom line The chat failures are not a mod regression. Symptom 2 is worked around by ChatInputFixPatch; symptom 1 by ChatVivoxSendFixPatch, which sidesteps the race at the point of use — it routes outgoing chat through the group text channel instead of the race-fragile per-recipient direct-message loop, and adds the matching ChannelMessageReceived subscription. Voice chat is untouched. The underlying un-awaited async race in the game's Vivox lifecycle is still worth an upstream report — the game devs can fix it in three lines with an await.

The two symptoms

Symptom 1 · fixed Chat sends nothing

Messages appear to send — the sender sees their own line — but no other player receives it. An un-awaited channel-lifecycle race leaves the adapter's participant list empty, so its per-recipient send loop reaches nobody. Worked around by ChatVivoxSendFixPatch.

Symptom 2 · fixed Chat input is "eaten"

A player who goes AFK for even a second can no longer use chat; keystrokes vanish and Enter stops opening the box. Caused by a stale text-editor selection plus a latched character state.

Symptom 2 — Mechanism

UI.Chat.TextChatVE.GetMessage() blanks the field while it still holds focus and a live cursor:

UI.Chat/TextChatVE.cs — decompiled
public string GetMessage()
{
    string text = ((TextInputBaseField<string>)(object)inputField).text;
    ((BaseField<string>)(object)inputField).value = "";   // cursorIndex/selectIndex still index the OLD string
    return text;
}

TextChatVE.HideInput() only toggles CSS classes:

UI.Chat/TextChatVE.cs — decompiled
public void HideInput()
{
    ((VisualElement)this).RemoveFromClassList("text-chat__active");
    inputContainer.AddToClassList("chat-log-input__disabled");
}

There is no Blur() and no SelectNone() anywhere in the chat code. The UIElements panel therefore keeps routing keydown events into a hidden text editor whose selection range now points past the end of an empty string. The next keystroke throws:

Why it's permanent, not transient

Gameplay.Chat.TextChat.OpenChat early-returns unless the "TextChatting" character state is false:

Gameplay.Chat/TextChat.cs — decompiled
if (!StateManager.GetState(((Component)LocalPlayer.I).gameObject, "TextChatting"))
{
    SetInput(); _chatUI.ShowInput(); _frameOpened = Time.frameCount; _chatOpened = true;
}

SetInput() sets that state true; only RemoveInput() clears it — and RemoveInput() is itself guarded:

Gameplay.Chat/TextChat.cs — decompiled
private void RemoveInput()
{
    if (Object.op_Implicit((Object)(object)LocalPlayer.I))
    {
        InputActionMapRequests.RemoveRequest(this);
        StateManager.SetState(((Component)LocalPlayer.I).gameObject, "TextChatting", false);
        _textingEnabled = false;
    }
}
The latch If LocalPlayer.I is momentarily null (respawn, scene transition) the cleanup silently skips, the flag stays true, and OpenChat refuses on every subsequent Enter. Nothing else in the codebase resets it. There is no timeout and no recovery path.

There is no AFK system

Grepped the full decompiled source for AFK, Afk, IdleTimer, idleTime, AwayFromKeyboard, InactivityTimeout — zero hits outside unrelated AI code (ActTimedIdle). "AFK" is the community's name for what is actually a window-focus / state-latch symptom. The log's --- OnApplicationFocused: False / True lines come from MenuScreenController.OnApplicationFocus.

Fix shipped

Implemented in VoidCrewTerminus/Patches/ChatInputFixPatch.cs:

PatchTargetEffect
PostfixTextChatVE.GetMessageSelectNone() + Blur() after the field is blanked
PostfixTextChatVE.HideInputSame, for closing chat without sending
PrefixTextChat.OpenChatClears a stale "TextChatting" state via the game's own RemoveInput()

The prefix works precisely because OpenChat dereferences LocalPlayer.I — by then the player reference is alive, so the cleanup that failed earlier now succeeds.

Degradation Config gate: EnableChatInputFix (default on). All members resolved via AccessTools with one-shot logging, so a game update that moves the vanilla UI makes the fix inert and says so rather than failing CreateAndPatchAll.

Symptom 1 — the send path

Ground truth is the decompiled adapter under .voidcrew/decompiled/Assembly-CSharp/; SDK behaviour is cited to docs.unity.com / docs.unity3d.com. The game ships Unity.Services.Vivox (the modern com.unity.services.vivox package), verified against VoidCrew.GameLibs 1.3.0.

VivoxAdapter.SendTextMessage does not send a channel message. It iterates the adapter's own locally-maintained participant list and sends one directed message per recipient, then locally echoes:

VivoxAdapter.cs:360-374 — decompiled
public void SendTextMessage(string message)
{
    if (!channelUsers.TryGetValue(textChannel, out var value))
    {
        return;                       // (A) hard fail — no echo either
    }
    foreach (VivoxParticipant value3 in value.Forward.Values)
    {
        if (!value3.IsSelf && !blocked)
            VivoxService.Instance.SendDirectTextMessageAsync(value3.PlayerId, message, null);
    }
    FireMessageReceivedEvent(VivoxService.Instance.SignedInPlayerId, message);   // (B) local echo — always runs past (A)
}

FireMessageReceivedEvent raises OnMessageReceived, which TextChat turns into a chat-log line (TextChat.cs:83-93, 238-244). It is the only local-echo path — TextChat.SendMsg() adds nothing to the UI itself, and VoidManager's chat patches are additive.

So the reported symptom — sender sees their own line, nobody else receives it — pins the failure to one specific state:

State at send timeGuard (A)Loop (B) sendsLocal echoMatches report?
textChannel == ""fails—no✗ (no echo)
textChannel set, not a key in channelUsersfails—no✗ (no echo)
textChannel set, key present, dict empty / self-onlypassesnothingyes✔
textChannel set, key present, remote participant presentpasses1+ DMsyes✗ (works)
Correction to the original note The earlier draft said the race leaves textChannel empty (row 1). If that were the real state, SendTextMessage returns at guard (A) before the echo — the sender would see nothing either. The observed “my line shows, theirs don't” is row 3: a _chat entry that exists in channelUsers but never received the remote player's ParticipantAddedToChannel. Rows 1–2 are a stricter, distinct failure (chat looks completely dead). All three are reachable from the same race.

Directed vs. channel messages — the fragility is the local dict, not Vivox. Unity's docs state a directed message “can be sent to any signed-in user independent of being in a channel together” (Directed messages). The per-recipient calls would themselves succeed — the failure is purely that the loop has no PlayerIds to iterate, because channelUsers[textChannel] is the game's own bookkeeping and the race emptied it. A channel message (SendChannelTextMessageAsync(channelName, …)) needs only the channel to exist with text capability and carries no dependency on channelUsers (Channel messages). That is the seam the fix uses.

The un-awaited race

VoipBoostrap.OnJoinedRoom discards the Task from LeaveChannels() and calls JoinChannels() synchronously:

VoipBoostrap.cs:93-101 — decompiled
public void OnJoinedRoom()
{
    Debug.Log((object)("[VIVOX] JOINED ROOM: " + PhotonNetwork.CurrentRoom.Name));
    VoipService.Instance?.LeaveChannels();      // returns Task — discarded, never awaited
    if (VoipService.Instance != null)
    {
        VoipService.Instance.JoinChannels();    // runs synchronously, immediately
    }
}

LeaveChannels() does its teardown synchronously and only then starts the async leave:

VivoxAdapter.cs:439-453 — decompiled
public Task LeaveChannels()
{
    AudioChannel = "";
    textChannel  = "";                                // synchronous clear
    channelUsers.Clear();                            // synchronous clear
    Task result = VivoxService.Instance.LeaveAllChannelsAsync();   // in flight; caller discards it
    OnLeaveCahnnels?.Invoke();
    return result;
}

JoinChannels() then fires two more un-awaited Tasks (VivoxAdapter.cs:411-429). The ChannelJoined / ChannelLeft / ParticipantAddedToChannel event callbacks that mutate textChannel and channelUsers land on later frames, and there is no documented ordering between an in-flight LeaveAllChannelsAsync and a JoinGroupChannelAsync issued before it resolves (IVivoxService).

A second inconsistency LeaveChannels() clears textChannel; LeftChannel (the ChannelLeft handler, VivoxAdapter.cs:144-148) only does channelUsers.Remove(channel) — it never clears textChannel. A ChannelLeft that arrives without a matching LeaveChannels() call (the tail of an earlier async leave, or SDK-initiated teardown during connection churn) removes channelUsers[textChannel] while textChannel keeps pointing at the now-absent key — row 2 of the send-path table, hard fail, no echo. Distinct from the row-3 symptom, and a session can move between them.
The SDK agrees this pattern is unsafe Unity's Vivox changelog: 16.2.0 (2024-03-19) — “Fixed an issue where leaving and immediately rejoining a channel result[ed] in an exception being thrown due to not being completely disconnected from the channel yet.” 16.5.4 (2024-12-18) — “a bug where trying to join multiple channels quickly would lead to an exception.” Both patterns are present verbatim in OnJoinedRoom → JoinChannels. (CHANGELOG)

The interleave

Timeline from OnJoinedRoom, main thread unless noted. The order of the four event groups is not guaranteed.

execution order
Frame N  (PhotonHandler.Dispatch -> IMatchmakingCallbacks.OnJoinedRoom)
  L1  LeaveChannels():  AudioChannel="" ; textChannel="" ; channelUsers.Clear()
                        t_leave = LeaveAllChannelsAsync()      <- in flight, discarded
  J1  JoinChannels():   JoinGroupChannelAsync("<room>_audio", AudioOnly, MakeActive)   <- in flight
                        JoinGroupChannelAsync("<room>_chat",  TextOnly,  MakeActive)   <- in flight
  OnJoinedRoom returns.  channelUsers is EMPTY, textChannel == "".

Frames N+1 ... N+k   (any order)
  E-JoinC   ChannelJoined("<room>_chat")   -> textChannel = "<room>_chat"
                                              channelUsers.Add("<room>_chat", {})   <- entry exists, EMPTY
  E-PartC   ParticipantAddedToChannel(remote in _chat) -> channelUsers["<room>_chat"] gains the peer
  E-Leave   t_leave resolves -> ChannelLeft("<room>_chat") -> channelUsers.Remove("<room>_chat")
                                              textChannel NOT touched -> still "<room>_chat"

If E-Leave lands after E-JoinC and the SDK does not re-emit E-PartC for the remote player (from its view nothing changed, or the 16.2.0 “not completely disconnected yet” defect corrupted the join), the resting state is textChannel set but channelUsers has no _chat key → row 2. If E-Leave was effectively a no-op (nothing joined when it ran) and the rapid _audio+_chat join tripped the 16.5.4 defect, E-PartC for the remote player never arrives → channelUsers["<room>_chat"] stays empty → row 3, the reported symptom.

The captured log excerpt is the E-Leave-after-J1 ordering — the two [VIVOX] Joining channel lines are logged synchronously inside JoinChannels, then the discarded t_leave resolves and its ChannelLeft callbacks run:

Every way in

Not just first join — the un-awaited leave→join shape recurs, and every reconnect re-arms it:

PathCodeShape
Room join / rejoinVoipBoostrap.OnJoinedRoom
VoipBoostrap.cs:93-101		LeaveChannels() (discarded) → JoinChannels() synchronously. Fires on every join for the life of the process.
Return to main menuVoipBoostrap.GameStateChanged
VoipBoostrap.cs:108-114		LeaveChannels() only (discarded). A later room join then races its tail.
Vivox reconnect helperVivoxReconnect.Recovered
VivoxReconnect.cs:22-44		if (ActiveChannels.Count < 2) { LeaveChannels(); JoinChannels(); } — both Tasks discarded, no await. Identical defect, fires after connection recovery.
Connection recoveryVivoxAdapter.OnLoggedIn → CheckRoom
VivoxAdapter.cs:431-437, 589-595		JoinChannels() with no preceding leave — relies on prior state being clean.
Vivox hard reconnectVivoxAdapter.Reconnect
VivoxAdapter.cs:540-587		The one path that gets it right: await LeaveChannels(), await LogoutAsync(), then JoinChannels().

So the bug is reproducible on first join and re-armed by every reconnect, recovery, and menu→game transition — consistent with the community reports where a full restart is the reliable workaround (Steam — “VoIP doesn't work”).

The capability red herring

The decompiled join passes raw enum casts:

VivoxAdapter.cs:426-427 — decompiled
VivoxService.Instance.JoinGroupChannelAsync(… + "_audio", (ChatCapability)1, val);
VivoxService.Instance.JoinGroupChannelAsync(… + "_chat",  (ChatCapability)0, val);

The published online docs for some Vivox versions list AudioOnly = 0, TextOnly = 1, which would mean the game joins its _chat channel with text disabled — a candidate primary cause. Checked against the shipped SDK and refuted: reflecting Unity.Services.Vivox.dll from VoidCrew.GameLibs 1.3.0 gives

Unity.Services.Vivox 1.3.0 — reflected
ChatCapability.TextOnly     = 0
ChatCapability.AudioOnly    = 1
ChatCapability.TextAndAudio = 2

So (ChatCapability)0 for _chat is TextOnly — correct, and (ChatCapability)1 for _audio is AudioOnly — correct. The channel capabilities are not the bug. The race is the sole cause.

A second, independent way chat can fail to arm

TextChat.OnEnable subscribes the chat hotkeys only inside an async continuation:

Gameplay.Chat/TextChat.cs — decompiled
VoipService.Instance.ChatEnabled.ContinueWith(delegate(Task<bool> task) {
    if (task.IsFaulted) Debug.LogError(...);
    if (task.Result) EnableChatInput();      // rethrows if faulted; continuation dies here
});

ChatEnabled is a property that starts a fresh task on every access (PAL.Privileges.HasCommunicationsPrivilege(false)), so the three call sites get unrelated tasks with no ordering between them. The continuations also run on the ThreadPool — no TaskScheduler.FromCurrentSynchronizationContext(), which VivoxAdapter itself passes correctly elsewhere — so InputAction.performed delegate lists get mutated off the main thread. A disable/enable pair landing out of order leaves the component enabled with zero handlers attached, and Enter does nothing.

This one is not addressed by the shipped fix — it is a separate arming race in TextChat, not the send path. Left documented; a targeted patch would need to serialise the ChatEnabled continuations onto the main thread.

Fix shipped

Implemented in VoidCrewTerminus/Patches/ChatVivoxSendFixPatch.cs. It does not try to reorder the game's async lifecycle — it neutralises every end state of the race at the point of use:

PatchTargetEffect
PrefixVivoxAdapter.SendTextMessageResolve the live _chat channel — the private textChannel field, else a scan of VivoxService.ActiveChannels for a key ending _chat — and send one SendChannelTextMessageAsync to it. No dependency on channelUsers. Keeps the same local echo via the game's own FireMessageReceivedEvent(signedInId, text). Returns false (falls through to vanilla) on any doubt: disabled, unresolved members, no channel name, or a thrown exception.
PostfixVivoxAdapter ctorSubscribe VivoxService.ChannelMessageReceived and forward every message with FromSelf == false into FireMessageReceivedEvent(msg.SenderPlayerId, msg.MessageText). The game only wires up DirectedMessageReceived, so without this the receive side would miss channel messages.
PostfixVivoxAdapter.DisposeUnsubscribe that handler. Re-attach on any later adapter re-creation (handlers are never stacked).

Why the seam is safe. A channel message needs only that the channel exists with text capability (Channel messages) — and The capability red herring above confirmed _chat is joined TextOnly. Delivery no longer depends on the adapter's participant bookkeeping, which is exactly what the race corrupts. The ActiveChannels scan also covers rows 1–2 (empty / stale textChannel).

Blast radius on voice: nil Voice is the separate _audio channel, muting, and speech detection — none of that code is on this path. SendTextMessage is text-only, and the patch never touches the join/leave lifecycle.
Degradation Config gate: EnableVivoxTextSendFix (section fixes, default on). All private members resolved via AccessTools with one-shot resolve logging, so a game update that moves VivoxAdapter makes the fix inert and says so rather than failing CreateAndPatchAll. A faulted SendChannelTextMessageAsync is logged once with a hint that the channel may lack text capability.
Still worth an upstream report The root cause is VoipBoostrap.OnJoinedRoom (and VivoxReconnect.Recovered) discarding the leave Task. The game devs can fix it with an await; the mod-side patch is a workaround over a private field and async lifecycle, brittle across game updates by design.

VoidManager is orthogonal

Its README's only chat claims, verbatim:

  • Unlocks mouse while using text chat
  • Chat input history
  • Command Auto-complete via tab key-press

The plugin description says "minor Chat improvements". The word "fixes" does not appear.

All three of its chat patches are postfix-only and purely additive:

PatchTargetPurpose
ChatCommandDetectPatchTextChatVE.GetMessageRoute / commands
PublicCommandDetectPatchTextChat.IncomingMessageParse ! commands
TextChatVEPatchShowInput / HideInputRaise ChatWindowOpened/Closed events

Nothing prefixes, transpiles, or replaces OpenChat, SetInput, RemoveInput, EnableChatInput, DisableChatInput, OnEnable, or OnDisable. Nothing touches the "TextChatting" state or field focus.

Aggravating, not causal CursorUnlock is driven by the ShowInput/HideInput postfixes, so if the game latches into a state where HideInput never runs, VoidManager leaves the cursor unlocked — which makes the breakage feel worse but is not its cause.

VoidCrewTerminus is not implicated

This mod only consumes VoidManager.Chat.Router to register commands. Its full Harmony target list is gameplay/UI-context only:

What could not be determined

  • InputActionsGameConfigTable is a ScriptableObject loaded from Resources, so which actions are enabled/disabled per input state lives in an asset, not in code. A third candidate mechanism — InputActionMapRequests promoting MenuScreenController above TextChat on the request stack and disabling the very actions needed to escape — is therefore plausible but unconfirmed. Related defects visible in code: SetTopState() skips entirely when the request list empties (last state stays latched), and MenuScreenController only ever calls AddOrChangeRequest, never RemoveRequest.
  • The engine-internal step from "exception during dispatch" to "all later keydowns dropped" is inferred from Unity's issue reports, not read from source. The stale-index throw is proven; the exact dispatcher state left behind is not.
  • The chat UXML/USS is not available, so whether chat-log-input__disabled sets display: none — which would change the focus semantics — is unverified.
  • VoidManager 1.2.11's binary was not inspected (only 1.2.7 and 1.2.10 are in the local NuGet cache). Chat strings are identical between those two and the master-branch source is labelled 1.2.11, so drift is unlikely but unconfirmed.
  • Upstream issue tracker not fully checked. Nihility-Shift/VoidManager reports 0 issues, but its README badges point at Void-Crew-Modding-Team/VoidManager, which may hold the real tracker. Not checked.
  • No deterministic repro was found for either symptom. Both are timing-dependent. The fixes are therefore reasoned from source, not validated against a reproduction.
  • The exact resting state of the Symptom 1 race (row 1 vs 2 vs 3 of the send-path table) needs the full VoidCrewTerminus-LogOutput-2026-07-20_*.log pair, which is not in the repo. Decisive evidence: whether a [VIVOX] Joined channel: <room>_chat appears after the last Left channel: <room>_chat, and whether any [VIVOX] Adding participant … (channel: <room>_chat) ever names a remote PlayerId. The shipped fix does not depend on which row it is — it covers all three.
  • Thread affinity of Vivox events. No first-party doc page reached states which thread ChannelJoined / ParticipantAddedToChannel / ChannelMessageReceived fire on. Assumed Unity main thread from the game's own un-locked Dictionary use and its single TaskScheduler.FromCurrentSynchronizationContext() call site; the fix's receive handler makes the same assumption vanilla's DirectedMessageReceived handler already does.
  • Whether the SDK re-emits ParticipantAddedToChannel after a same-name leave/rejoin. This is the hinge of the “participant list never repopulates” mechanism. Not documented; not testable without a repro build.
  • Which Unity Vivox package version Void Crew bundles. The ChatCapability enum was pinned from VoidCrew.GameLibs 1.3.0's Unity.Services.Vivox.dll; the CHANGELOG defects cited are 16.2.0–16.5.4 (2024). The game's own un-awaited leave→join is upstream of any SDK fix regardless.
