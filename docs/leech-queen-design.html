Leech Queen — System Design

Design VoidCrewTerminus mod Void Crew 1.3.0 Not scheduled

Technical design for the Leech Queen — a fourth Pilgrimage boss whose projectile volleys trigger module shutoffs inside the player ship while a swarm consumes the crew's capacity to fix them. For the intent-level companion, see leech-queen-rfc.html. Vocabulary is defined in handoff/CONTEXT.md.

Context

The TODO file at the project root names a wish under the Leech block: “boss leech queen”. This design realises it as a boss that shares the Leech's art language and origin fiction while depending on none of the Leech runtime, which is itself unbuilt.

Status Design only. Not scheduled. Implementation is gated on explicit user go-ahead, matching the Leech Carrier and Aux Fighter features. Three of this mod's designed features are currently unbuilt; this is the third.

Dependencies on existing mod systems, all shipped:

SystemUsed for
Sector EscalationIsScalingActive is the Queen Gate.
BossDefeatHookProgression credit. Requires no changes — it keys off EndlessQuest.IsBossObjective, not off any specific asset.

System Summary

A vanilla boss prefab is instantiated as normal by the vanilla boss objective. The mod then re-dresses it — swapping visible geometry for an authored mesh — and replaces its ability list with a composed set of projectile volleys and swarm spawns. Volley impacts on the player ship trigger a module shutoff at the point of contact. Vanilla's critical-component system provides weak points that permanently silence attacks. Nothing about the boss's structure, hit points, colliders, AI framework or network identity is authored by the mod.

Vanilla Foundations

Everything in this section was read from .voidcrew/decompiled/ against Void Crew 1.3.0. Anything not readable from source is called out explicitly and routed to Pre-Flight.

Boss generation

Pilgrimage is QuestType.Pilgrimage, generated by EndlessQuest. A boss section fires on the last sector of a solar system:

// Gameplay.Quests/EndlessQuest.cs
private bool ShouldGenerateBossSection()
    => context.SectorsUsedInSolarSystem + 1 == context.SectorsToUseInSolarSystem;

private void PrepareBossSectionParameters()
{
    BossObjectiveConfig randomBossObjective =
        parameters.SolarSystemBosses
                  .GetOptionsForSolarSystem(parameters.SolarSystems[context.ActiveSolarSystemIndex])
                  .GetRandomBossObjective(context.Random);
    context.NextSectionParameters.MainObjectiveCount  = 1;
    context.NextSectionParameters.ViableMainObjectives = new List<ObjectiveDataRef> { randomBossObjective.Objective };
    context.NextSectionParameters.ViableSectors        = new List<Sector> { randomBossObjective.Sector };
    context.NextSectionParameters.UseBossDrops        = true;
    // ...
}

Two facts follow, both load-bearing:

  • Bosses are keyed per solar system. BossConfig.GetOptionsForSolarSystem throws if a system has no options, and each SolarSystemBossOptions holds a List<BossObjectiveConfig>. A BossObjectiveConfig is just { ObjectiveDataRef Objective; Sector Sector; } — an objective plus an arena.
  • Generation happens at runtime, one section ahead. EndCurrentSection() calls GenerateNextSection() each time a section ends. So the Queen Gate can read live escalation state, with one section of lead time. It does not need to be decided at quest construction.

The roll itself is uniform, with no weight field:

// Gameplay.Quests/SolarSystemBossOptions.cs
public BossObjectiveConfig GetRandomBossObjective(Random rnd)
    => BossOptions[rnd.Next(0, BossOptions.Count)];
Consequence Simply appending to BossOptions yields 1/(n+1) and nothing else. Since n is authored ScriptableObject data, if each live system holds exactly one boss then appending makes the Queen a 50% coin flip. A configurable weight therefore requires patching the pick rather than mutating the list. See Patch Surfaces.

Boss AI framework

The “sits in one spot and cycles attacks” archetype is already factored:

TypeRole
HpDrivenBossSignalResolverAdvances PhaseData.CurrentPhase from HP thresholds; also advances it in OnBehaviourEnd when a CastAbilitiesSequentiallyPhaseDrivenBeh completes a cycle. Owns OnAggroAbilityIndicesToActivate.
AIHpDrivenPhaseTransition{ PhaseIndex, HPThresholdPercent }. A list of these defines the phase ladder.
CastAbilitiesSequentiallyPhaseDrivenBeh
CastAbilitiesRandomlyPhaseDrivenBeh		Per-phase ability rotation behaviours.
ActiveShootProjectilesAbilityProjectile volleys through NpcShooter, with WeaponIndices, ShootPatternOverride and ShootSequenceOverride.
SpawnReinforcementsAbilitySwarm spawning via NpcAISpawn. Carries ShouldSpawnsDieWhenAIDies, delayBetweenSpawnsDeaths, DistributionSettings, PositioningConfig, SendsAttackCommandToSpawns.
RepairDestroyableComponentsAbilityLets a boss heal its own criticals. Held for a future variant.

BaseNpcAbility is a plain [Serializable] class, not a ScriptableObject, held in a [SerializeReference] List<BaseNpcAbility> Abilities on NpcAI. The mod can therefore construct abilities with new, append them, and subclass for bespoke behaviour. Two hard limits apply:

Ability constraints 1. Sixteen abilities maximum, total. NpcAbilitiesActiveValuesMask() packs one bit per ability index into a short, and NpcAI logs an error above 16. The Queen's attacks spend from the host boss's remaining budget.

2. Ability order must be byte-identical on every client. WriteAbilitiesData / ReadAbilitiesData are positional against a shared PhotonStream: a mask is written, then each active ability's payload in index order. One extra or missing ability does not merely desync that ability — it corrupts every read after it.

Weak points

Vanilla already implements “destroy the sub-structures to kill the boss”:

// CriticalDestroyableComponentController.cs
public List<DestroyableComponent> CriticalDestroyableComponents;

private void OnTrackedDestroyableDestroyed(DestroyableComponent destroyed)
{
    runtimeTrackedDestroyables.Remove(destroyed);
    if (Ship.photonView.AmController && runtimeTrackedDestroyables.Count <= 0)
        Ship.ApplyRawDamage(Ship.HitPoints, null);   // all criticals dead -> boss dies
}

DestroyableComponent exposes a public Action<DestroyableComponent> OnKilled, plus MirrorDamageToParent, HideHealthBar, IsInvulnerable and DefenseType. Wiring “this critical dies → that attack stops” is a subscription, not new machinery.

Not readable from source: whether a given vanilla boss prefab carries a CriticalDestroyableComponentController at all, and how many components are in its list. Authored prefab data. Routed to pre-flight.

The shutoff effect

RandomShutoffBehavior already defines exactly the effect the Queen needs, and its recovery loop:

  • It only ever turns a module off. Restoring power is the crew's job; the burden never restores it. There is no affliction state, no duration, nothing to expire.
  • It already exposes a trigger: public void TriggerImmediately(), used by the !triggerburden dev command.
  • The player notification already exists and is driven by the module's real power state via PowerDrain.IsOn.OnChange, never by the timer — so a vetoed request can never announce a shutoff that did not happen.
  • Authority is owner, not host. CellModule.TurnOff() is PowerDrain.IsOn.RequestChange() — a local ChangeResponsive request, vetoable by ChangeValidators, owner-authoritative, replicated by vanilla PowerDrain sync. The file documents that ticking on non-owners causes thrash.
Required seam RequestPowerOff() is private, and RandomShutoffBehavior only exists on modules burdened by a cursed relic — which most modules are not. The effect must be lifted out of the behaviour into a shared helper so that the burden's timer and the Queen's projectile impact become two triggers of one effect. Same extraction that already moved EnemyScalingHelpers out of Features/Forge/.

Escalation interaction

EnemyDensityPatch patches only AIDirector.Set/AddSpawner{Target,MaxTarget}Intensity. SpawnReinforcementsAbility spawns through NpcAISpawn, bypassing AIDirector entirely — therefore the Queen's swarm is not amplified by density escalation at any scalar. Her numbers are authored.

Her hit points are a different story: EnemyStatScalingPatch postfixes DestroyableComponent.InitializeHealth for Hollow/Remnant faction objects, and TODO line 18 records that boss exclusion was deferred because the ObjectiveData→spawned-ship link needed another pre-flight pass. This feature needs that link regardless, so it closes that debt.

Queen Gate

Two conditions, evaluated at boss-section generation time:

  1. SectorEscalation.IsScalingActive — i.e. BossesDefeated >= BossActivationThreshold (default 2). While dormant, the Queen does not exist in the run at all.
  2. A weighted roll at QueenBossWeight (default 25%), drawn from context.Random.
Determinism Drawing from context.Random — the quest's own seeded generator, which already drives GetRandomBossObjective — means every client computes the same result from the same seed and the same escalation state. No ModMessage is required for the gate, provided escalation state is already synced, which ForgeNetSync guarantees. Consuming a draw from context.Random does shift the generator's stream, so the gate must be evaluated identically on every client or subsequent generation diverges — it must not be conditional on anything local.

She is eligible in every live solar system, and reuses whichever system's boss Sector she rolled into. One Host Skeleton is shared across all of them — she is the same creature wherever she nests.

Host Skeleton

The vanilla boss is instantiated by the vanilla objective, unmodified. The mod intervenes afterwards, on the spawned instance:

Stays vanillaBecomes the mod's
OrbitObject, hit points, MaxHitPointsVisible Renderer geometry (swapped)
Colliders and hit volumesNpcAI.Abilities contents
DestroyableComponents and their placementPhase ladder values
NpcAI, signal resolver, aggroMaterials, VFX, audio
PhotonView and network identityReward drop
Art constraint Weak-point placement is inherited. The authored mesh must be modelled so that its readable features — sacs, vents, launcher clusters — land on top of the skeleton's existing DestroyableComponent transforms. Otherwise a player shoots a glowing sac and nothing happens, or shoots flat plating and kills a critical. The skeleton choice is therefore a prerequisite for the art work, not parallel to it.

Bundle-loaded materials need the same shader relink the Forge already performs — ModulePrefabGrafter.RelinkShaders re-resolves each material's shader by name against the live build, without which bundle materials render solid black under any light.

Ability Composition

Her attack set is composed from existing ability classes wherever possible, spending from the 16-slot budget. Indicative composition:

SlotAbilityPurpose
Volley AActiveShootProjectilesAbilityPrimary line volley. Phase 1 onward.
Volley BActiveShootProjectilesAbilitySecond pattern, different arc. Phase 3.
SwarmSpawnReinforcementsAbilityAttention-tax adds. Phase 2 onward.
Brood PathActiveShootProjectilesAbility subclassOptional. Parasite volley; only registered when the Leech runtime exists.
Registration order Because serialisation is positional, Brood Path cannot be registered from a per-player config read. Its presence must travel with host-broadcast state, exactly as DifficultyScalar does. Registration order must be a fixed, literal sequence in code — never a dictionary walk, never a reflection scan, never conditional on anything a client decides locally.

Whether the volleys need a bespoke subclass at all depends on how projectile impact is detected — see below. A custom subclass is viable and needs no Photon type registration, because ability payloads travel through the parent's stream via WriteData/ReadData rather than as serialised custom types.

Impact → Shutoff

The core mechanic, and the only genuinely new logic in the feature.

1. Detect the impact

Queen projectiles hitting the player ship arrive through the damage path. DestroyableComponent.ApplyHitDamage(float damage, OrbitObject source, DamageType damageType, Vector3 point, Quaternion rotation, bool friendlyFire) carries both the source and the impact point — enough to identify a Queen hit and locate it in world space.

2. Select the victim module (host)

The host resolves the CellModule whose position is nearest the impact point. Host arbitration is mandatory here: if each client picked independently, clients would disagree about which module went dark. Candidate filtering — skip already-dark modules, skip modules the crew deliberately powered down, apply a minimum re-trigger interval per module — belongs entirely on the host.

3. Route to the module's owner

The host broadcasts the decision keyed by photonView.ViewID. The owner of that module performs the shutoff, because PowerDrain.IsOn is owner-authoritative. This is the PendingByViewId pattern already used by ForgeNetSync for views that have not yet resolved locally.

4. Apply the effect

The owner calls the extracted shutoff helper: request IsOn = false, log declines loudly (a vetoed RequestChange is otherwise a silent no-op — the failure mode that left Phase 6's density scaling dead for a whole phase), and let the existing PowerDrain.IsOn.OnChange handler produce the player notification from the real power state.

5. Recovery

Nothing. Recovery is the crew walking to the module and switching it back on — identical to a normal RandomShutoff, with no mod-side state to clear.

Why there is no affliction state An earlier iteration of this design tracked per-module afflictions with durations, stacking rules and expiry, all needing sync. Modelling the impact as a trigger of an existing effect rather than an application of a new one deletes that entire subsystem. Note that writing into ForgeSnapshot.Burdens instead would be actively wrong: WithBurdenAdded is idempotent per type and burdens persist for the run, so each module could be hit exactly once, permanently — the attack would become a no-op within seconds and a won fight would leave the ship crippled.

Swarm

A single SpawnReinforcementsAbility, configured as an attention tax rather than a threat:

  • ShouldSpawnsDieWhenAIDies = true with the built-in delayBetweenSpawnsDeaths stagger — no mop-up phase after the kill, which matters because the crew jumps immediately from a boss sector.
  • Weak, numerous, low damage. No drops.
  • SendsAttackCommandToSpawns so they engage without waiting to acquire.
  • Not amplified by density escalation (see Vanilla Foundations), so swarm size is a pure tuning value.

Phases & Criticals

Three AIHpDrivenPhaseTransition entries form the spine. Each phase adds; destroyed criticals subtract.

PhaseTriggerActive
1AggroVolley A
2HP thresholdVolley A + Swarm
3HP thresholdVolley A + Volley B + Swarm, higher cadence

Each CriticalDestroyableComponent is mapped to one ability. On its OnKilled, that ability is permanently deactivated and excluded from future phase rotations. The mapping must be host-arbitrated in the sense that all clients derive it from the same fixed table — the ability must remain present in the list (positional serialisation) and merely inert.

Degradation path If the chosen skeleton carries fewer criticals than there are abilities to map, the surplus abilities simply have no silencing critical. If it carries none, or no controller at all, the encounter runs as HP-phases-only. Identity survives; a layer is lost. This must be verified before the art brief is written, since it also determines what the mesh needs to make shootable.

Reward Drop

Vanilla boss drops proceed untouched (UseBossDrops = true and the chapter drop config are already set by PrepareBossSectionParameters). On top, a host-rolled chance at a Legendary Cursed Relic carrying a Queen Signature Perk.

  • Host-arbitrated roll, following CursedRelicSpawnPatch and RelicReplicationPatch, which already establish that all relic RNG belongs to the host.
  • Tier is forced to Legendary and must bypass SectorEscalation.DowngradeRelics — the whole point is a guaranteed-tier trophy, and the loot reshape would otherwise be entitled to downgrade it.
  • Cursed, so its perk pool includes downside perks and it can attach a Maintenance Burden. Thematically her signature following the crew home.
  • Signature Perk registered in PerkPool against that relic identity, so it rolls only for her relic.

Architecture

The feature lives in its own directory and does not reach into Features/Forge/. The one shared thing — the shutoff effect — is extracted to a neutral location first.

Dev commands

Non-negotiable for testability: she is gated behind two boss defeats and a weighted roll, so she cannot be reached reliably by playing.

  • !queenspawn — force the next boss section to resolve to the Queen.
  • !queentrigger — fire a volley immediately, or apply an impact at a named module.
  • !queeninfo — dump gate state, live phase, and which criticals have silenced which abilities.
  • !bossoptions — dump SolarSystemBosses per system. Doubles as the pre-flight tool below.

Pre-Flight Verification

Blocking All of the following require a live install. The reference-only NuGet Assembly-CSharp.dll has empty method bodies, and none of these facts are in .voidcrew/decompiled/ — two of them are authored ScriptableObject/prefab data that no decompiler can produce.
  1. Boss options inventory. Dump BossConfig.SolarSystemConfig per live solar system: how many BossOptions each holds. Decides whether a weighted pick is required (it almost certainly is) and what appending would actually cost.
  2. ObjectiveData→spawned-ship link. The blocker deferred at TODO line 18. Establish how to get from the active boss objective to the spawned boss OrbitObject. Everything else depends on this. Also unblocks boss exclusion from stat scaling.
  3. Critical component inventory per boss prefab. For each of the three vanilla bosses: does it carry a CriticalDestroyableComponentController, and how many components? Selects the Host Skeleton and determines whether the weak-point layer exists at all.
  4. Existing ability count per boss prefab. How many of the 16 NpcAI.Abilities slots vanilla already uses on the chosen skeleton. Determines the Queen's actual budget.
  5. Skeleton geometry. Export the chosen skeleton's collider layout and weak-point transforms as the art brief's reference frame.
  6. Player-ship impact path. Confirm that DestroyableComponent.ApplyHitDamage is the path NPC projectiles take into player-ship components, and confirm which clients it runs on.
  7. Module ownership. Confirm who owns a player-ship CellModule's PhotonView in practice, so the shutoff routing targets the right peer.

Phased Plan

Phase 0 Pre-flight

All seven items above, against a live install. Nothing else starts until item 2 is solved — without the objective-to-instance link there is no boss to modify. Output: skeleton selection, ability budget, weak-point inventory, art reference frame.

Phase 1 Shutoff extraction

Lift the effect out of RandomShutoffBehavior into Features/Modules/ModuleShutoff.cs. Behaviour becomes a trigger over the shared effect. Pure refactor — no behaviour change, verified by existing burden tests plus !triggerburden. Ships independently of the rest.

Phase 2 Gate + substitution

QueenGate and the PrepareBossSectionParameters postfix. Substitute a vanilla boss objective as a stand-in so the roll can be proven before any Queen content exists. Test: !queenspawn forces it; the gate stays shut while escalation is dormant; two clients agree on every roll.

Phase 3 Boss reach + stat exclusion

Use the Phase 0 link to get the spawned instance. Add boss exclusion to EnemyStatScalingPatch, closing the TODO line 18 debt. Test: a boss at scalar 6 has vanilla hit points.

Phase 4 Ability composition

QueenAbilityBuilder: deterministic construction, fixed order, 16-slot budget enforcement. Volleys and swarm, no interior effects yet. Test: two clients, extended fight, no ability desync; a deliberate order mismatch is caught by the budget/order assertion rather than by corrupt reads.

Phase 5 Impact → shutoff

QueenImpactHandler plus the new message. Host selects victim, owner executes via ModuleShutoff. Test: volley impacts darken the nearest module on all clients; declines are logged; the cooldown prevents the same module being hammered.

Phase 6 Phases + criticals

Phase ladder and the critical-to-ability silencing map, including the HP-only degradation path. Test: destroying a mapped critical permanently stops that attack, on both clients; all criticals destroyed kills her via the vanilla controller.

Phase 7 Body

Blender authoring against the Phase 0 reference frame, bundle export, QueenBodyBuilder, shader relink. Test: she renders correctly under sector lighting; shooting a visually-readable feature kills the critical underneath it.

Phase 8 Reward

Signature perk registration, host-rolled Legendary cursed drop, downgrade bypass. Test: the relic drops at Legendary at any scalar; its signature perk rolls only for it; all clients see one relic.

Phase 9 Tuning

Playtest with crews of two, three and four. The specific thing being measured is whether the crew ever loses on queue length rather than on a mistake. Primary knob is QueenShutoffCooldown, then swarm size, then volley cadence.

Test Plan

Unit (xunit, no Unity)

  • QueenGate: shut while dormant; opens at threshold; weight honoured; same seed → same result across repeated evaluation.
  • Critical-to-ability map: silencing is idempotent; unmapped criticals are no-ops; all-silenced leaves a valid rotation.
  • Ability order: the builder produces a byte-identical sequence for identical inputs, and rejects a build exceeding the slot budget.
  • Victim selection: nearest-module resolution given a point and a module set; already-dark modules skipped; cooldown respected.

In-game, solo

  • Gate shut before escalation; open after; !queenspawn forces the encounter.
  • Volley impact darkens the expected module and produces the existing notification.
  • Crew restore works; no mod state lingers afterwards.
  • Phase ladder advances on HP; criticals silence attacks; all criticals kills her.
  • Reward drops at Legendary; signature perk rolls only for that relic.
  • BossDefeatHook counts her — BossesDefeated increments, scalar bumps.

In-game, two clients

  • Both clients roll the Queen for the same seed, and both see the same body and ability list.
  • Sustained fight with no ability desync — specifically, no ability behaving as though reading another's payload.
  • A shutoff decided by the host appears on the correct module on both machines.
  • Late joiner mid-fight receives the silencing map and sees the correct phase.
  • Host migration mid-fight: the new host continues arbitrating impacts.
  • One relic drop total, not one per client.
